# Clicky Windows — Phase 1 Plan (Decisive)

## Context

Clicky Windows is the **first polished Windows port** of Farza Majeed's [Clicky](https://github.com/farzaa/clicky) (macOS, 3.5K stars, MIT). The macOS original captures your screen on a push-to-talk hotkey, sends it to Claude, animates a blue cursor to UI elements via Claude's Computer Use API, and speaks the response. The #1 community demand on the upstream repo is a Windows version (Issue #26, 18 comments, 2 forks). The #2 demand is **persistent memory** (Issue #30 — "stateless Claude wrapper, no memory between sessions") — that is **the differentiator** that makes this not just a port. The previous Claude Code session (3,838 lines, transcript at `Claude Code Clicky Chat.txt`) already did the deep research, locked the strategy, wrote `CLAUDE.md`, and saved this `STARTER_PROMPT.md`. This session's job is **execution** — write the lean documentation set, then build Phase 1 component-by-component with manual verification.

## Strategy (revised after user pushback)

**Old plan (wrong):** Phase 1 = Python loop only → Phase 2 = Tauri rewrite + memory.

**New plan (right):** **One Python build, MVP includes persistent memory from day 1.** No rewrite. If validation succeeds → harden Wallee-style (more tests, replay scenarios, real users, polish). If validation fails → iterate or throw away.

**Why one phase, not two:**
- The user is right: shipping "Clicky core loop on Windows" is not differentiation. Mushtaq Bilal already vibe-coded that hack in 2 hours. The differentiator — persistent memory — has to be in the MVP, not deferred.
- Wallee proves Python at 3K LOC + 517 tests clears the B0 bar. There's no language-based reason to rewrite to Tauri. The rewrite was an aesthetic choice driven by my over-anchoring on Grafyn, not on what the project actually needs.
- The MVP needs to answer **"is Clicky+memory better than Clicky?"** not **"can a Python script capture a screenshot?"**

**Revised phase shape:**

| Phase | What it is | Goal | Done when |
|---|---|---|---|
| **Phase 1: MVP (1-2 weeks)** | Python: capture + Computer Use API + overlay + STT + TTS + hotkey + **SQLite memory** + recall pipeline | Validate the differentiated hypothesis: "memory makes Clicky meaningfully better" | 5+ real user sessions where memory recall noticeably improved the experience, recorded as a demo video |
| **Phase 2: Harden (2-4 weeks, if Phase 1 validates)** | Same Python codebase, add: 50-100+ tests (Wallee-style replay scenarios), proactive mode, BYOK, clipboard copy, configurable hotkey UI, PyInstaller bundle, install path, "unexpected finding" writeup | Match the B0 bar by **rigour proportional to problem**, not by rewriting | Bar checklist met, 5+ users, writeup published, install path tested |
| **Phase 3 (only if needed): Tauri rewrite** | Only triggered if Phase 2 hits a Python-specific wall (install experience too rough, performance too slow, threading deadlocks) | Production polish | TBD |

**This is the user's actual ask:** "I want to see as a validation the MVP. BUT, if we just copy existing clicky then what is even the point, don't even bother building. The goal is to build something better."

### 2. Architecture — locked

| Layer | Choice | Why |
|---|---|---|
| Language | Python 3.13 | Fastest path to a working loop. Tauri rewrite is Phase 2. Already user-decided. |
| Screen capture | `mss` | Multi-monitor, cross-platform, ~5ms per capture. Cursor position via `ctypes.windll.user32.GetCursorPos`. |
| DPI | `SetProcessDpiAwareness(2)` (per-monitor v2) at startup | Per-monitor DPI is mandatory on modern Windows. Without this, the pointer is in the wrong place on the secondary monitor. |
| Resolution selection | **Aspect-ratio-aware**: pick from `[(1024,768), (1280,800), (1366,768)]` based on actual display ratio | **Mirror original Clicky exactly.** They proved this matters — distortion kills X-axis accuracy. Captured directly from `ElementLocationDetector.swift`. |
| Resize | PIL `Image.resize(LANCZOS)` to **exact pixel dimensions** | Mirror Clicky's "no Retina doubling" approach. Send Claude exactly what we declare. |
| Hide overlay before capture | Always | If we don't, Claude sees its own pointer in the screenshot and tries to point at it. |
| Vision call | **Claude Sonnet 4.6 with Computer Use API** (`tools=[{"type":"computer_20251124", ...}]`, `anthropic-beta: computer-use-2025-11-24`) | **Reversing my earlier plan.** Original Clicky uses this for pixel-perfect coordinates because Computer Use activates Claude's specialized pixel-counting training. Vision-only with regex tags is meaningfully less accurate. |
| Coordinate clamping | Always clamp to (0,0)–(declared_w, declared_h) before scaling | Claude occasionally returns slightly out-of-bounds coords. Clicky does this. |
| STT | **`faster-whisper` `base` model**, CPU | 4× faster than `openai-whisper` (CTranslate2 backend), drop-in API. Same model quality. **Changing CLAUDE.md's `openai-whisper` recommendation** — append a DECISIONS.md entry. |
| TTS | `pyttsx3` (SAPI) | Free, offline, instant. ElevenLabs is Phase 2. |
| Hotkey | **`Alt+Space`**, push-to-talk, suppressed via `pynput.keyboard.Listener(suppress=True)` low-level hook | User-confirmed. Fallback if Alt+Space conflicts: `Ctrl+Shift+Space`. |
| Overlay | PyQt6 + Win32 layered window styles via `ctypes`: `WS_EX_LAYERED \| WS_EX_TRANSPARENT \| WS_EX_TOPMOST \| WS_EX_NOACTIVATE \| WS_EX_TOOLWINDOW` | Qt's `WA_TransparentForMouseEvents` alone is not enough on Windows for true click-through. Layered window flags applied after window creation. |
| Pointer animation | `QPropertyAnimation`, linear easing, 400ms | Bezier polish is Phase 2. |
| Multi-monitor | Capture monitor under cursor; overlay spans full virtual desktop; sort displays cursor-first when telling Claude (mirrors Clicky) | Day-1 multi-monitor support is mandatory because Windows users routinely have 2+ monitors. |
| Threading | Qt event loop on main thread; pynput listener thread; worker threads for audio/Whisper/Anthropic; cross-thread comms via Qt signals only | Single rule: **no UI calls from worker threads, ever.** PyQt6 is not thread-safe. |
| Memory | **Karpathy-style: markdown files in `~/.clicky-windows/memory/` (one `.md` per app) + SQLite index for fast lookup** | Combines Wallee's rigour (SQLite for indexing) with Karpathy's "no fancy RAG, just markdown files Claude can read" philosophy. Each app gets a running log: `EXCEL.EXE.md`, `chrome.exe.md`, `photoshop.exe.md`. Claude reads the relevant `.md` directly into context on each interaction (no embedding, no retrieval). SQLite indexes (app_name, last_used, interaction_count) for fast lookup of "have I seen this app before, and how much." User can read the markdown files themselves to see what Clicky remembers. |
| API key | `.env` via `python-dotenv`. **Anthropic-direct only in Phase 1** (Computer Use API beta requires it). No proxy. | Single-user prototype. Cloudflare Worker proxy is Phase 2 (when shipping to others). |
| Provider abstraction | **Wrap each external service in a small class** so Phase 2 can swap implementations without touching `app.py`: `class AIClient` (Phase 1 = AnthropicClient with Computer Use, Phase 2 adds OpenRouterClient with vision-tag fallback), `class STT` (Phase 1 = FasterWhisper, Phase 2 adds AssemblyAI), `class TTS` (Phase 1 = Pyttsx3, Phase 2 adds ElevenLabs) | Mirror Wallee's `BuddyTranscriptionProvider` protocol pattern. ~30 min extra now, ~10 hours saved in Phase 2. The classes are tiny — just one method each: `ask()`, `transcribe()`, `speak()`. |
| Screenshot strategy | **Phase 1 = always send screenshot.** Phase 2 = add diff-and-skip caching (hash last screenshot, skip API if unchanged). Phase 2/3 = add UIA accessibility tree fast path for productivity apps, fall back to screenshot for creative apps. | Premature optimization is the root of all evil. Get the high-quality baseline working first, optimize once it's measurable. |
| Git | `git init` + private GitHub repo via `gh repo create --private` | User-confirmed. Commit at end of each step. |

## Build Sequence (no step is "done" without acceptance proof)

### Step 0 — Scaffold
- `requirements.txt` — `anthropic`, `mss`, `PyQt6`, `pynput`, `sounddevice`, `numpy`, `faster-whisper`, `pyttsx3`, `Pillow`, `python-dotenv`
- `.env.example` (`ANTHROPIC_API_KEY=`), `.gitignore` (`.env`, `__pycache__/`, `*.pyc`, `debug_*.jpg`, `whisper-cache/`)
- `config.py` — env loading + `HOTKEY="alt+space"`, `WHISPER_MODEL="base"`, `CANDIDATE_RESOLUTIONS=[(1024,768),(1280,800),(1366,768)]`, `MODEL_ID="claude-sonnet-4-6"`, `COMPUTER_USE_BETA="computer-use-2025-11-24"`
- `pip install -r requirements.txt`
- `git init`; `gh repo create clicky-windows --private --source=. --remote=origin --push`
- **Acceptance:** all imports work, repo visible in `gh repo view`

### Step 1 — `capture.py`
- `set_dpi_awareness()` — call at module import via `ctypes.windll.shcore.SetProcessDpiAwareness(2)`
- `get_cursor_position()` — `ctypes` `GetCursorPos`
- `pick_resolution(width, height)` — return `(target_w, target_h)` whose aspect ratio is closest to `width/height` (mirror Clicky)
- `capture_active_screen()` — uses mss, returns `(PIL.Image, monitor_dict, cursor_xy)` for the monitor under the cursor
- `resize_for_claude(img, target_w, target_h)` — PIL `LANCZOS` resize to **exact pixel dims**, returns `(resized, scale_x, scale_y)`
- `unscale_coords(x, y, scale_x, scale_y, monitor)` — Claude coords → physical desktop coords
- **Verification:** `python -m capture` → saves `debug_capture.jpg`, prints monitor + cursor + chosen resolution + scale factors. User mouses over a known UI element and confirms cursor coords match.
- **Acceptance proof:** screenshot is correct monitor, dimensions match chosen resolution, cursor coords printed match real position ±2 px

### Step 2 — `ai.py`
- **`class AIClient` (abstract base):** single method `ask(image, transcript, history, declared_w, declared_h) -> dict`. Returns `{"text": str, "points": [...]}` regardless of which provider implements it.
- **`class AnthropicClient(AIClient)`:** Phase 1 implementation. Uses Anthropic SDK directly with Computer Use API beta.
- Phase 2 will add `class OpenRouterClient(AIClient)` with vision-tag regex fallback (no Computer Use beta on OpenRouter).
- Anthropic implementation: sends image as base64 + transcript + system prompt (copied/adapted from Clicky's `ElementLocationDetector.swift`)
- `tools=[{"type":"computer_20251124","name":"computer","display_width_px":declared_w,"display_height_px":declared_h}]`
- Header `anthropic-beta: computer-use-2025-11-24`
- Parses `tool_use` blocks with `{"action":"left_click","coordinate":[x,y]}`
- Clamps coords to `[0, declared_w] × [0, declared_h]` before returning
- Returns `{"text": str, "points": [{"x":int,"y":int,"label":str}]}` (still in declared resolution; caller scales back)
- Maintains in-memory `history` list
- **Verification:** load `debug_capture.jpg`, ask "what's on my screen and point at the most clickable thing"
- **Acceptance proof:** API call succeeds, ≥1 coordinate parsed, coordinates inside bounds, response text non-empty

### Step 3 — `overlay.py` (highest risk)
- `OverlayWindow(QWidget)` — frameless, transparent background, always-on-top, no taskbar entry, click-through, spans full virtual desktop
- After `show()`, apply Win32 styles via `ctypes.windll.user32.SetWindowLongW` with `GWL_EXSTYLE` ORing in `WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_TOPMOST | WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW`
- `point_at(x_physical, y_physical, label)` — `QPropertyAnimation` from current pos to target, 400ms linear
- Custom-painted blue arrow + label
- `hide_for_capture()` / `show_after_capture()`
- **Verification:** `python -m overlay` opens overlay, animates pointer through 3 hardcoded coords spanning the virtual desktop. User confirms (a) clicks pass through to apps below, (b) pointer visible + smooth, (c) no taskbar entry, (d) doesn't steal focus when shown
- **Acceptance proof:** all four confirmed manually
- **Fallback if PyQt6 click-through is unreliable:** raw `pywin32` + `tkinter` with `-transparentcolor`

### Step 4 — `stt.py`
- **`class STT` (abstract base):** `start_recording()`, `stop_and_transcribe() -> str`
- **`class FasterWhisperSTT(STT)`:** Phase 1 implementation
- Phase 2 will add `class AssemblyAISTT(STT)` for streaming
- `record_until_release(stop_event) -> np.ndarray` — 16kHz mono via `sounddevice`
- `transcribe(audio) -> str` — `faster_whisper.WhisperModel("base", device="cpu", compute_type="int8")`
- Lazy singleton at module import (avoid 2-3s reload latency)
- Pre-warm audio device at app startup (avoid first-record dropout)
- **Verification:** `python -m stt` records 5s, prints transcript. User says "hello world how are you."
- **Acceptance proof:** transcript matches spoken words, latency <2s for 5s of audio

### Step 5 — `tts.py`
- **`class TTS` (abstract base):** `speak(text: str)` (blocking or threaded, caller decides)
- **`class Pyttsx3TTS(TTS)`:** Phase 1 implementation
- Phase 2 will add `class ElevenLabsTTS(TTS)`
- `speak(text: str)` — pyttsx3, runs in background thread when called from main loop, voice rate ~180 wpm
- **Verification:** `python -m tts` speaks "Hello, I am Clicky Windows."
- **Acceptance proof:** audible

### Step 6 — `hotkey.py`
- `register(on_press, on_release)` — `pynput.keyboard.Listener(suppress=True)` watching for Alt+Space
- Push-to-talk semantics: hold to record, release to fire
- **Verification:** `python -m hotkey` prints PRESSED / RELEASED. User confirms system menu doesn't open.
- **Acceptance proof:** events fire, no system-menu interference. **If suppression flaky → fall back to Ctrl+Shift+Space, log decision in DECISIONS.md, surface to user.**

### Step 6.5 — `memory.py` (Karpathy-style markdown memory + SQLite index)
- Memory directory: `~/.clicky-windows/memory/` (created if missing)
- One markdown file per Windows app: `EXCEL.EXE.md`, `chrome.exe.md`, `photoshop.exe.md`
- File format: append-only log with timestamps, user question, Clicky's response, what was pointed at:
  ```
  ## 2026-04-11 14:30
  **Window:** Book1 - Excel
  **User asked:** how do I save this file
  **I said:** the Save button is in the top-left corner, I'm pointing at it now
  **I pointed at:** Save button (450, 80)
  ```
- SQLite index at `~/.clicky-windows/index.db` for fast lookup:
  ```sql
  CREATE TABLE apps (
    app_name TEXT PRIMARY KEY,
    first_seen TEXT,
    last_seen TEXT,
    interaction_count INTEGER,
    md_path TEXT
  );
  ```
- Functions:
  - `init_memory()` — creates `~/.clicky-windows/memory/` and `index.db` if missing
  - `get_active_app() -> (app_name, window_title)` — via `ctypes.windll.user32.GetForegroundWindow` + `GetWindowTextW` + `GetWindowThreadProcessId` + `GetModuleFileNameExW`
  - `record(app_name, window_title, user_question, claude_response, points)` — appends to the app's `.md` file, updates SQLite index
  - `recall(app_name) -> str` — reads the app's `.md` file (last 2-3KB) and returns it for injection into Claude's system prompt
  - `infer_skill_level(app_name) -> str` — based on `interaction_count`: "first-time" (0) / "beginner" (1-3) / "familiar" (4-10) / "experienced" (11+)
  - `get_summary() -> dict` — for debug / future settings UI: list all apps with counts
- **Why markdown not pure SQLite:** user can open `EXCEL.EXE.md` and read what Clicky remembers about them. Karpathy's principle: "the LLM writes and maintains all of the data, you rarely touch it directly, but it's human-readable when you want it." Also makes Phase 2 lint scripts trivial.
- **Verification:** `python -m memory` → seed 3 fake interactions for "EXCEL.EXE", call `recall`, print formatted output, open the `.md` file by hand and confirm it looks human-readable
- **Acceptance proof:** `.md` file exists and is human-readable, `recall` returns last N entries as a string, `infer_skill_level` returns the right bucket, SQLite index is updated

### Step 7 — `app.py` (integration — 2nd highest risk)
- Startup: `set_dpi_awareness()`, load Whisper (worker thread), pre-warm audio, init overlay, init pyttsx3, register hotkey
- On hotkey press: hide overlay, start recording, optional listening cue
- On hotkey release:
  1. Stop recording, transcribe (worker thread)
  2. Capture screen, pick resolution, resize
  3. **Get active window title (`memory.get_active_window`)**
  4. **Call `memory.recall(app_name)` and inject into system prompt**
  5. Call `ai.ask_claude(image, transcript, history, recall_context, ...)` (worker thread)
  6. Scale coords back from declared resolution → physical → into overlay's coordinate space
  7. Animate pointer to each point sequentially, brief pauses
  8. Speak response (concurrent with animation)
  9. **Call `memory.record(...)` to persist this turn**
  10. Append turn to in-session history list (still kept in memory for the current run)
- **Strict threading rule:** workers emit Qt signals; only the main thread touches UI
- **Verification (end-to-end):** open Excel (or any app), hold Alt+Space, say "what's on my screen and how do I save", release. Within ~7s see pointer animate to Save while voice describes it.
- **Acceptance proof:** 3 successful runs in a row on a real app without crashing. Recorded as a screen capture for the README.

### Step 7.5 — `tools/lint_memory.py` (Karpathy-style health check)
- Standalone CLI script, not part of the main app
- Scans `~/.clicky-windows/memory/*.md`, calls Claude with the contents, asks: "summarize what this user has been struggling with, what patterns repeat, what would proactive guidance look like for them"
- Writes the output to `~/.clicky-windows/insights.md`
- Run by hand weekly (`python tools/lint_memory.py`)
- **Why this exists:** copies Karpathy's literal pattern. The goal is to find the **unexpected finding** that becomes the B0 case study — not to ship a feature. The lint script is the lens that reveals it. Two-hour build, massive payoff.
- **Verification:** seed 10 fake interactions across 2 apps, run lint, confirm output is non-trivial
- **Acceptance proof:** `insights.md` contains a meaningful summary, not just "you used Excel 5 times"

### Step 8 — Polish
- Bug fixes from end-to-end runs
- `README.md` written based on what actually works
- Demo screen recording
- **Use the app yourself for at least 5 sessions on a real task** (learn a new app, debug something, etc.) before declaring Phase 1 done
- **Run `lint_memory.py`** at the end of those 5 sessions and read `insights.md` — that's where the unexpected finding will surface

## Risks & Mitigations

| # | Risk | Probability | Mitigation |
|---|---|---|---|
| 1 | PyQt6 click-through unreliable on Win11 | High | Apply Win32 layered window flags via ctypes after show(); fallback to tkinter+pywin32 |
| 2 | Per-monitor DPI breaks pointer position | Very High | `SetProcessDpiAwareness(2)` at startup; document coord-space conversions in DECISIONS.md |

| 5 | Threading deadlocks | High | Strict rule: only Qt signals cross thread boundaries; review every cross-thread call |

## Grafyn deep-dive details (for Phase 2 reference)

I just deep-dived [WKJBryan/Grafyn](https://github.com/WKJBryan/Grafyn) — Bryan's project that the user explicitly named as the bar. Honest summary, then the tension it creates for this plan.

### What Grafyn actually is
- **Tech stack:** Tauri 1.8 + Rust backend (19,088 LOC, 54 `.rs` files, 13 IPC command modules, 65 IPC commands) + Vue 3 frontend (10,784 LOC, 42 components) + Pinia + D3.js + Vitest + Tantivy 0.22 (full-text) + petgraph (graph) + Playwright E2E (1,078 LOC, 6 spec files) + native Rust MCP server bundled as separate binary + OpenRouter for multi-model
- **Code volume:** ~29,900 LOC across 135 files. Largest file is `link_discovery.rs` at 1,815 LOC. Feature-folder organization (`commands/`, `services/`, `models/`), not layer-based.
- **Tests:** **123 Rust unit tests** + 1,078 LOC of Playwright E2E + Vitest frontend tests
- **CI/CD:** 4 GitHub Actions workflows. `test.yml` runs 6 parallel jobs on every PR (preflight, Rust tests, frontend tests, lint+clippy, security audit, build). `release.yml` is a 4-platform matrix (Windows x64, Windows ARM64, macOS ARM64, Linux x64), builds the MCP binary separately, uploads to Cloudflare R2, generates an updater manifest, verifies the endpoint. `release-smoke.yml` builds on every PR. `latest-deps.yml` does weekly forward-compat dependency testing.
- **Release discipline:** Semantic versioning, **9 releases (v0.0.3 → v0.1.8) in 63 days**, two-phase release flow (prepare PR with version bumps + Cargo.lock regen → merge → tag), conventional commits with PR refs, no tag reuse ever
- **Documentation:** **22.3 KB CLAUDE.md** (~4,500 words) covering architecture diagram, full IPC command reference table, frontend API client structure, wikilink + 9 typed link relations, note status workflow, distillation pipeline, three link-discovery algorithms, multi-LLM canvas with semantic context injection + streaming, conversation import (4 platform parsers), temporal + graph-aware retrieval, settings runtime sync, MCP architecture, CI walkthrough, **known CI pitfalls** (Tauri v1 + Ubuntu 22.04 quirks, Cargo.lock commit requirements), release rules. Plus `WORKING_GUIDE.md`, `TESTING_PROGRESS.md`, `HOW_TO_RUN.md`, separate READMEs per package.
- **Production signals:** Auto-updates via Cloudflare R2, offline feedback queue with retry, graceful MCP fallback (read-only when desktop holds the lock), GitHub Issues integration
