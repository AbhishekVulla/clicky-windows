The critique is correct. Clicky Windows is a "press hotkey, ask, see pointer, done" tool — not a structured course with a progression ladder. Slapping a `beginner`/`intermediate`/`expert` label on the user was:

1. **Paternalistic** — the `< 5` / `5..20` / `> 20` thresholds were invented without any validation that they correspond to real skill transitions

3. **Not in the Phase 1 acceptance criteria** — the hypothesis is "memory recall makes the demo noticeably better," NOT "Claude adapts its vocabulary to skill level"
4. **Pre-digesting data the LLM can read directly** — if Claude sees the raw markdown tail via `recall()`, it can infer engagement depth from the actual history without us labeling it

This is a Karpathy "wait for the data" decision. If 5+ real sessions later reveal that Claude adapts poorly without an explicit skill signal, we can revisit. For now, delete the code.

## Research pass (upfront, not ceremony — cheap reads before writing code)

Per `feedback_ceremony_vs_lean.md` "Research is NOT ceremony" section: for any component that touches an external SDK or stdlib API, verify method signatures and behavior against installed source BEFORE writing code that depends on them. For memory.py this is:

1. **`sqlite3` stdlib (Python 3.13 built-in).** Known-stable API I've used dozens of times; no installed-source read needed:
   - `sqlite3.connect(path, isolation_level=None)` → autocommit mode, simpler than manual `BEGIN`/`COMMIT`
   - `PRAGMA journal_mode=WAL` → better concurrent-read safety + crash resilience (Phase 2 proactive mode will want this)
   - `CREATE TABLE IF NOT EXISTS` + `CREATE INDEX IF NOT EXISTS` → idempotent schema migration on every startup
   - Parameterized queries with `?` placeholders ONLY (NEVER f-string SQL — obvious injection hole)
   - `conn.row_factory = sqlite3.Row` → dict-like access for `list_known_apps()`
2. **`pathlib.Path`** — `Path.mkdir(parents=True, exist_ok=True)` for the memory dir, `Path.read_text(encoding="utf-8")` / `Path.write_text(..., encoding="utf-8")` for the markdown files.
3. **`datetime`** — `datetime.now().strftime("%Y-%m-%d %H:%M")` for markdown headers and SQLite columns. Zero timezone complexity in Phase 1 (single user, single machine).
4. **Karpathy LLM-KB philosophy** — already cited verbatim in `DECISIONS.md` "Karpathy-style markdown memory + SQLite index hybrid" entry: *"I thought I had to reach for fancy RAG, but the LLM has been pretty good about auto-maintaining index files and brief summaries of all the documents and it reads all the important related data fairly easily at this small scale."* No vector DB, no embeddings, no RAG. LLM writes, LLM reads, human can `cat` the files.
5. **Existing config** — `config.py` lines 130-144 already defines `MEMORY_DIR`, `INDEX_DB_PATH`, `INSIGHTS_PATH`, `MEMORY_RECALL_MAX_CHARS = 3000`. memory.py reads these; no config changes needed.
6. **app.py injection shape (from memory py.txt line 156-165)** — the Step 7 orchestrator will call `memory.recall(app_name)` + `memory.infer_skill_level(app_name)`, format them into the `text` content block BEFORE the current user question, send as a single Claude message. memory.py does NOT do the injection itself; it just returns strings. Single responsibility.

**No subagents needed for research.** Every item above is either stdlib I already know or a config/design decision locked in existing files. This research pass is me confirming the premises, not gathering new info.

## Public API (inherited verbatim from the pre-compact `memory py.txt` design)

```python
from pathlib import Path
from typing import Literal

class MemoryStore:
    def __init__(
        self,
        memory_dir: Path = MEMORY_DIR,
        index_db_path: Path = INDEX_DB_PATH,
    ) -> None:
        """Ensure memory_dir + SQLite schema exist. Idempotent; safe to
        construct on every app launch. Does NOT open a persistent connection
        — each method opens its own short-lived connection so concurrent-read
        Phase 2 proactive mode doesn't need lock coordination with the Qt
        main thread."""

    def recall(self, app_name: str, max_chars: int = MEMORY_RECALL_MAX_CHARS) -> str:
        """Read the TAIL (last max_chars characters) of
        ~/.clicky-windows/memory/<sanitized_app_name>.md. Returns '' if the
        file doesn't exist. Caller (app.py Step 7) injects this into the
        Claude user-message text content block, NOT the system= param —
        Computer Use beta requires the instructions to be co-located with
        the image per Clicky's ElementLocationDetector.swift pattern."""

    def record(
        self,
        app_name: str,
        window_title: str,
        user_question: str,
        claude_response: str,
        pointer_targets: list[tuple[int, int]],
    ) -> None:
        """Append a new interaction block to the app's markdown file,
        update SQLite (first_seen on first-ever record, last_seen always,
        interaction_count += 1). Creates the file + directory lazily on
        first call. Sanitizes user_question / claude_response / window_title
        for safe markdown embedding (replaces triple backticks with triple
        single-quotes; escapes internal newlines in the single-line fields)."""

    def list_known_apps(self) -> list[dict]:
        """SELECT * FROM apps ORDER BY last_seen DESC. Returns list of dicts
        with keys: app_name, first_seen, last_seen, interaction_count, md_path.
        Used by tools/lint_memory.py (Step 7.5) and future Phase 2 proactive mode."""

    def infer_skill_level(
        self,
        app_name: str,
    ) -> Literal["beginner", "intermediate", "expert"]:
        """Heuristic bucket from interaction count in SQLite:
          <  5   → 'beginner'     (initial discovery phase)
          5..20  → 'intermediate' (has asked enough questions to know basics)
          > 20   → 'expert'       (deep engagement)
        Unknown app (no SQLite row) → 'beginner'. Phase 2 may add question-
        complexity heuristics; Phase 1 is interaction-count-only because that's
        the signal Phase 1's 5+ real sessions can actually validate."""
```

## File format — `~/.clicky-windows/memory/excel.exe.md`

```markdown
# Excel — Clicky Memory

First seen: 2026-04-01 10:23
Interactions: 17
_(This file is human-readable. Delete it to reset memory for this app.
  Clicky reads the tail of this file to remember past interactions.)_

## 2026-04-12 14:30 — "how do I freeze the top row"
Window: Sales Q1 - Excel
Response: Click View tab, then Freeze Panes → Freeze Top Row in the ribbon.
Pointed at: (1245, 82)

## 2026-04-12 14:15 — "how do I sort this column alphabetically"
Window: Sales Q1 - Excel
Response: Select the column, click Data tab → Sort A to Z.
Pointed at: (892, 110)
```

**File header is rewritten on every `record()`.** Implementation: read the existing file if present, split into `(header_block, interaction_blocks)` on the first `## ` heading, update the `First seen` / `Interactions` lines in the header, concatenate `[new_header, *old_interactions, new_interaction]`, write back. Header is 5-6 lines; rewrite cost is negligible (Phase 1 files are <100KB). The italic transparency line in the header is the Karpathy "human-readable, user can delete to reset" guarantee from the B0 differentiator pitch.

## SQLite schema — `~/.clicky-windows/index.db`

```sql
CREATE TABLE IF NOT EXISTS apps (
    app_name          TEXT PRIMARY KEY,     -- sanitized (lowercased, reserved chars replaced)
    first_seen        TEXT NOT NULL,        -- ISO 8601 string "YYYY-MM-DD HH:MM"
    last_seen         TEXT NOT NULL,
    interaction_count INTEGER NOT NULL DEFAULT 0,
    md_path           TEXT NOT NULL         -- absolute path to the .md file
);
CREATE INDEX IF NOT EXISTS idx_apps_last_seen ON apps(last_seen DESC);
PRAGMA journal_mode=WAL;
```

**Why SQLite at all when the markdown files are the "real" memory:** `list_known_apps()` is the one operation that becomes slow without it — Phase 2 proactive mode will want "find the most recently-active app" without reading every markdown file. `infer_skill_level()` also needs interaction count without parsing the markdown. The SQLite index is a denormalized cache of facts derivable from the markdown, but cheaper to query. Source of truth remains the markdown files: if SQLite disagrees with the markdown (e.g. user manually deleted a `.md` file but the row still exists), `recall()` returns `''` for the missing file regardless of SQLite, and the next `record()` call re-inserts the row cleanly. Phase 2 `lint_memory.py` may add a `rebuild_index()` helper that re-scans all markdown files and re-syncs SQLite — not a Phase 1 concern.

## Gotchas handled upfront

1. **App-name sanitization.** `GetForegroundWindow()` process names can contain spaces, Unicode, or Windows-reserved chars (`<>:"/\\|?*`). `_sanitize_app_name(name: str) -> str` helper: lowercases the whole string, replaces any reserved char with `_`, strips leading/trailing whitespace, raises `ValueError` if result is empty. Stores the SANITIZED name as the SQLite primary key AND the markdown filename. The ORIGINAL (pre-sanitization) name is preserved inside the markdown header's `# <original> — Clicky Memory` line for human readability.
2. **Markdown code-fence injection.** Claude's response can contain triple-backticks. Escape by replacing triple-backticks with triple single-quotes (`'''`) in the `user_question` / `claude_response` / `window_title` fields before writing. Alternatives considered: zero-width-space insertion (too clever, Karpathy-unfriendly), HTML escape (breaks plain-text readability). Plain replacement wins.
3. **Single-line fields with embedded newlines.** `user_question` and `window_title` are rendered on a single markdown line each; replace embedded `\n` with `↵` (visible unicode marker) to preserve the block shape for the `lint_memory.py` parser. `claude_response` is multi-line-safe because it's written as its own `Response: ...` paragraph — but still fence-escape it.
4. **Concurrent writes.** Phase 1 has ONE writer (the Qt main thread via `app.py` Step 7). SQLite WAL mode handles this cleanly + fresh connection per call. No explicit locking in memory.py. Phase 2 proactive-mode concurrency is an open question for Step 7 app.py ceremony, not this plan.
5. **`last_seen` vs `first_seen` timestamp race.** Capture a single `datetime.now()` at the top of `record()` and pass the same string into both the markdown writer and the SQLite `UPSERT`. Prevents the micro-difference that would make sorting non-deterministic.
6. **Tail read on `recall()`.** `max_chars=3000` default. Implementation: `text = path.read_text(encoding="utf-8"); return text[-max_chars:] if len(text) > max_chars else text`. Files >100KB are not a Phase 1 concern (~100-300 interactions per app before hitting that size); `lint_memory.py` in Phase 2 can compact the oldest entries if needed.
7. **Atomic file writes.** `Path.write_text` is not atomic on Windows (no `fsync` guarantee). For Phase 1 this is acceptable — a crash during write loses the most recent interaction, not the file. Phase 2 may upgrade to `tempfile.NamedTemporaryFile` + `os.replace`. Documented as a known limitation.
8. **Empty pointer targets.** Phase 1 expects `pointer_targets: list[tuple[int, int]]`; empty list means Claude responded text-only ("no specific element"). The markdown renders that as `Pointed at: (none — text-only response)` instead of empty or missing — keeps the block shape consistent for Step 7.5 parsing.
9. **UTF-8 tail safety.** `text[-max_chars:]` can slice mid-codepoint in theory, but Python's `str` is already codepoint-indexed, not byte-indexed, so slicing a `str` never splits a character. Safe. (Would NOT be safe on a `bytes` slice.)
